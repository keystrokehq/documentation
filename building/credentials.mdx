Keystroke includes a built-in credential vault that stores API keys, service tokens, and OAuth connection data on behalf of your project. Instead of reading secrets directly from environment variables inside your actions, you define a typed credential schema and let the runtime resolve it at execution time. This keeps your action code clean, makes credentials portable across environments, and ensures values are encrypted at rest.

## How the vault works

When a workflow step or agent tool runs, Keystroke resolves each declared credential against the vault, decrypts the value, validates it against the schema you defined, and injects it into the `run` function. You declare what a credential looks like; the vault handles storage, retrieval, and OAuth token refresh.

Credentials are scoped — they can be set at the organisation level or the project level, and the runtime picks the most specific match.

## `defineCredential`

Use `defineCredential` to declare a credential schema. The schema describes the shape of the stored value so the vault knows how to validate it and your action code gets correct TypeScript types.

<ParamField body="key" type="string" required>
  The vault key name. Used as the identifier when you set the value with the CLI. By convention, use `SCREAMING_SNAKE_CASE`.
</ParamField>

<ParamField body="fields" type="ZodObject">
  A Zod object schema describing the fields inside this credential. Each key becomes a typed property available in your `run` function.
</ParamField>

### Example: custom API key

```ts
// src/credentials/custom-app.ts
import { defineCredential } from "@keystrokehq/keystroke/credentials";
import { z } from "zod";

export const customAppKey = defineCredential({
  key: "CUSTOM_APP_KEY",
  fields: { apiKey: z.string() },
});
```

You can define multiple credentials in a single file, or one per file — the convention is up to you. Export each one as a named export so it can be imported wherever it is used.

## Using credentials in actions

Attach credentials to a `defineAction` call using the `credentials` array. The runtime resolves each credential before calling `run` and passes the resolved values as a second argument.

```ts
// src/actions/call-custom-api.ts
import { defineAction } from "@keystrokehq/keystroke/action";
import { z } from "zod";
import { customAppKey } from "../credentials/custom-app";

export const callCustomApi = defineAction({
  slug: "call-custom-api",
  input: z.object({ query: z.string() }),
  output: z.object({ result: z.string() }),
  credentials: [customAppKey],
  run: async (input, { credentials }) => {
    const { apiKey } = credentials[customAppKey.key];

    const response = await fetch("https://api.example.com/search", {
      headers: { Authorization: `Bearer ${apiKey}` },
      method: "POST",
      body: JSON.stringify({ q: input.query }),
    });

    const data = await response.json();
    return { result: data.result };
  },
});
```

<Note>
  Actions are the primary place to declare and use credentials. Agents access credentials indirectly through the tools (actions) they are equipped with — you do not set credentials directly on `defineAgent`.
</Note>

## Setting credentials via the CLI

Once you have defined a credential schema, use `keystroke credentials set` to store a value in the vault. The CLI prompts you for each field defined in the schema.

```bash
# Interactive — prompts for each field
keystroke credentials set CUSTOM_APP_KEY

# Set individual fields inline
keystroke credentials set CUSTOM_APP_KEY --set apiKey=sk-...

# Scope to the current project only (default is org-level)
keystroke credentials set CUSTOM_APP_KEY --scope project --set apiKey=sk-...
```

You can list what is currently stored and inspect which credentials a workflow or agent depends on:

```bash
keystroke credentials list
```

<Warning>
  Credentials set locally (via `keystroke dev` or `keystroke start`) are stored in your local database. When you deploy to the cloud, credentials must be re-set against the cloud target — they are never uploaded with `keystroke deploy`. See the CLI reference for details.
</Warning>

## Built-in integration credentials

When you register an integration plugin in `keystroke.config.ts`, Keystroke manages its credential schema automatically. You do not call `defineCredential` for Slack or Google — you connect them through the OAuth flow.

<Tabs>
  <Tab title="Slack">
    After adding `slack()` to your config and setting the required environment variables, run the OAuth installation flow to connect a workspace. Keystroke stores the bot token in the vault and injects it into any Slack action at runtime.

    ```ts
    // keystroke.config.ts
    import { slack } from "@keystrokehq/slack";

    export default defineConfig({
      integrations: [slack()],
    });
    ```

    ```bash
    # Connect a Slack workspace via the dashboard OAuth flow, or:
    keystroke connect slack
    ```
  </Tab>
  <Tab title="Google">
    After adding `google()` to your config, users authenticate via the OAuth flow and Keystroke stores their access and refresh tokens. Token refresh is handled automatically.

    ```ts
    // keystroke.config.ts
    import { google } from "@keystrokehq/google";

    export default defineConfig({
      integrations: [google()],
    });
    ```

    ```bash
    keystroke connect google
    ```
  </Tab>
</Tabs>

## Static API key credentials

For third-party services that use simple API keys rather than OAuth, define a credential with a single `apiKey` field (or whatever fields the service requires) and set it once via the CLI.

```ts
// src/credentials/exa.ts
import { defineCredential } from "@keystrokehq/keystroke/credentials";
import { z } from "zod";

export const exaCredential = defineCredential({
  key: "EXA_API_KEY",
  fields: { apiKey: z.string() },
});
```

```bash
keystroke credentials set EXA_API_KEY --set apiKey=exa-...
```

<Tip>
  All credential values are encrypted at rest in the Keystroke vault. The raw secret is never stored in plain text and never included in build artifacts or deploy uploads.
</Tip>
